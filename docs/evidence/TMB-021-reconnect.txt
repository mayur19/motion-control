The test uses three local UDP endpoints and covers initial status/clock gating,
accepted synchronized motion, a second active player, immediate background
pause, deterministic heartbeat timeout, stable P1 assignment on a new endpoint,
fresh post-reconnect PING/PONG, continued P2 input, unchanged host session and
rejection of packets from the old endpoint. It also verifies that foreground
resume clears the old motion-port pin, resets the clock estimate, rejects early
motion, completes a fresh PING/PONG and restores motion acceptance.

Controller and host verification
--------------------------------

- Godot host smoke test: PASS (TMB-004_HOST_SMOKE_OK)
- iOS simulator build and tests: PASS (12 tests)
- iPhone 17e physical XCTest bundle: PASS (12 tests)

iOS uses a recurring 500 ms Network.framework STATUS send on the retained UDP
connection. Android sends at the same interval from its dedicated DatagramSocket
control thread. Both persist a random installation ID and report foreground,
sensor validity and measured sampling rate.

iOS now recreates its control connection and repeats HELLO after foreground
resume or a Network.framework path interruption. The reconnect attempt listens
for the path becoming ready and retries for up to 12 seconds. The host permits
the known installation to reclaim its active 15-second reservation after the QR
join window expires, while still rejecting expired codes for new assignments.

Physical iPhone evidence
------------------------
On 2026-11-06, an iPhone 17e physically paired over the LAN, synchronized its
clock and streamed at approximately 100 Hz. Backgrounding produced an immediate
Paused status, stopped motion acceptance and reached Disconnected after the
documented two-second timeout. The foreground-resume defect discovered during
this run was fixed and added to the automated integration test above.

A genuine camera QR run then streamed at 99.6 packets/s. Turning Wi-Fi off
produced `Paused` followed by `Disconnected`; motion later returned on a new UDP
port, but the retained control socket did not. That physical failure exposed a
second iOS defect: the host correctly kept the unsynchronized motion gated. The
control client now re-HELLOs on foreground/path recovery as described above.

The rebuilt app passed all 12 tests on the physical phone, paired again by
camera and reproduced the physical Wi-Fi disconnect. The phone remained off the
LAN past the 15-second reservation in the post-fix attempt. A later foreground
launch did exercise the fix: the controller automatically re-HELLOed on a new
control endpoint, reached Connected after fresh clock synchronization and
resumed motion at 81.1 packets/s before it was backgrounded again. Because that
occurred after the bounded reservation expired, the host issued a new controller
ID; same-reservation/same-player restoration is therefore not claimed yet. One
timely post-fix restore cycle and the Android/Galaxy matrix remain pending. No
automated result is represented as completed physical restore evidence.
